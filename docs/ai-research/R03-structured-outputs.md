# R03 — Structured outputs and schema design

Status: initial evidence notes, 2026-11-27. Documentation only. No changes to prompts, schemas, runtime options, parsing, saving, validation rules or feature contracts. See the [research index](README.md), [bibliography](references.md), and [R01 prompt structure](R01-prompt-structure.md).

## Scope and method

Structured output covers the model-to-application interface: the requested record shape, field meanings, generation format or decoding constraints, and the distinction between received material and completed application operations. This is separate from R01's question of how to structure *input* instructions.

This targeted pass reviews primary publication records and abstracts for P05 and P38–P48, together with the JSON Schema object reference. Conference papers and preprints are identified in the bibliography. It is not a systematic or full-text literature review. No benchmark replication or WebCap inference is required.

## Evidence

| Question | Published finding | Limits and relevance to WebCap |
| --- | --- | --- |
| Can constrained generation help? | [P05 — Geng et al. (EMNLP 2023)](https://aclanthology.org/2023.emnlp-main.674/) demonstrate grammar-constrained generation for information extraction, entity disambiguation and constituency parsing, with substantial gains over unconstrained models on those tasks. Input-dependent grammars can restrict outputs to task-specific choices. | Strong support for using known output structures in appropriate tasks. It does not establish better creative Scene prompts or justify treating model output as an executable instruction. The known vocabulary and actual destination remain application-owned. |
| Does a JSON Schema request guarantee conformance? | [P38 — JSONSchemaBench](https://arxiv.org/abs/2501.10868) evaluates six constrained-generation frameworks, including llama.cpp, using 10,000 real-world schemas and the official JSON Schema test suite. It separately measures supported constraints, efficiency and output quality. | A schema's expressive power and a runtime's supported subset are distinct. Requesting a schema is not evidence that every keyword is enforced, nor that a truncated or otherwise unsuccessful response will conform. The tested implementations/versions do not establish behavior of WebCap's current local or remote endpoints. |
| Does forcing a format affect the model's work? | [P39 — Tam et al. (EMNLP Industry 2024)](https://aclanthology.org/2024.emnlp-industry.91/) report reduced performance on reasoning tasks under format restrictions, with greater degradation under stricter restrictions. [P40 — Park et al. (NeurIPS 2024)](https://arxiv.org/abs/2405.21047) demonstrate that greedy grammar masking may change the distribution of valid continuations; their grammar-aligned algorithm improves model-likelihood alignment on tested tasks. [P41 — Schall and de Melo (RANLP 2025)](https://aclanthology.org/2025.ranlp-1.124/) report differing effects for base and instruction-tuned models, including reduced performance on generation tasks for some instruction-tuned models. | Structure, decoding strategy and task performance interact. None of these results demonstrates that every JSON output harms quality or that a particular WebCap schema is too restrictive. A grammatically valid result is not necessarily the best creative result. |
| Can structured generation retain reasoning capability? | [P42 — CRANE (ICML 2025)](https://proceedings.mlr.press/v267/banerjee25a.html) studies grammars that allow intermediate reasoning and reports gains on symbolic reasoning benchmarks. [P43 — Reddy et al. (ICML 2026)](https://proceedings.mlr.press/v306/reddy26a.html) study an unconstrained draft followed by constrained generation and report gains on structured reasoning tasks. [P44 — Nguyen et al. (2026 preprint)](https://arxiv.org/abs/2610.35328) distinguish formatting, validity and reasoning restrictions; their controlled comparisons challenge the assumption that decoder masking alone necessarily causes observed degradation. | These results qualify the preceding evidence: beneficial constraints and appropriate decoding are possible. The algorithms and tasks differ from WebCap's creative writing, visual extraction and tagging. They do not authorize extra draft calls, reasoning fields, retries, new decoders or repair passes. |
| Is the schema itself part of the instruction? | [P45 — Lin (2026 preprint)](https://arxiv.org/abs/2608.08254) compares placement of classification definitions in system prompts, user prompts and schema descriptions, finding model-dependent effects and losses when instructions conflict. [P46 — Le (AACL-IJCNLP 2026)](https://aclanthology.org/2026.aacl-long.116/) changes only schema-key wording in controlled experiments across seven models and two mathematical reasoning benchmarks; results vary by model and task, including positive and negative effects. | Field names, descriptions and prompt wording warrant joint consideration; a description is not guaranteed to reach or influence every runtime/model in the same way. Descriptive fields can help explain intended content, but no paper establishes a universal winning naming convention or instruction placement. No field rename or duplicate instruction is proposed. |
| Is a valid result a correct result? | [P47 — ExtractBench (2026 preprint)](https://arxiv.org/abs/2602.12247) distinguishes field-specific semantic correctness, array alignment, missing values and invented values in nested document extraction; broader schemas were challenging even for tested frontier models. [P48 — Structured Output Benchmark (2026 preprint)](https://arxiv.org/abs/2604.25359) reports a gap between high schema adherence and lower exact value accuracy across text-normalized source domains. | Particularly relevant to tags, Sight observations, QA findings and reference assessments. The model can return a valid enum that is visually wrong, a well-formed but ungrounded evidence reference, or a complete Scene record that is creatively weak. Extraction benchmarks do not assess the quality of open-ended production specifications. |

## Separate the four contracts

The following is a conceptual distinction for reading the research, not a new WebCap validation pipeline.

| Layer | What it establishes | What it does not establish |
| --- | --- | --- |
| Requested output schema | What fields, types, collections and alternatives the model is asked to produce. | That every field was meaningfully authored or every request was fulfilled. |
| Runtime generation and decoding | What output syntax or schema constraints the chosen runtime actually enforces. | Factual accuracy, artistic merit or successful persistence. |
| Received result and interpretation | What parseable values, usable records and actual errors were received. | Permission to write unselected fields or invent missing values. |
| Explicit application operation | What WebCap can actually assign, save or display under its existing operation contract. | That the model has certified the result's quality. |

The [JSON Schema object reference](https://json-schema.org/understanding-json-schema/reference/object) defines property presence and permitted extra keys: a property declaration alone is not a required field, a present null is not an absent field, and a required string may be empty unless a further constraint forbids it. These are standard semantics rather than empirical model-quality findings. Application meaning is separate: an omitted value, an intentionally empty value, an unknown observation, and an invalid value may call for different treatment according to the existing feature contract.

For creative output, asking for all the content the user needs and retaining independently usable received material are compatible goals. A required generation field need not imply rejecting every other received field when a provider fails to return it. For evidence extraction, a field should not force the model to invent an observation that cannot be supported. The meaning of absent, empty or unknown values is operation-specific; no universal required/optional policy follows from the literature.

## Open questions for later research or design

- Direct comparative evidence for complex creative fields and batches of independent Scene records, rather than extraction, math or classification.
- Support and actual handling of schema descriptions, optional properties, nested structures, output limits and partial responses by the specific local and remote runtime versions used in WebCap.
- How schema field meanings and model-facing task language interact in our specialized small-model workloads; preprints on schema instructions are preliminary evidence.
- How best to represent genuine uncertainty or absence in Sight and assessment outputs without forcing an unsupported value (R05/R09/R15).
- Evidence directly comparing field-level retention policies after incomplete generation. The reviewed papers do not establish a specific salvage algorithm or the desirability of extra recovery calls.

No changes to product behavior or new validation work are authorized. Next topic: R04 — in-context learning and examples.
