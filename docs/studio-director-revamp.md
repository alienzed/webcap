# Studio Director — conversational production contract and incremental delivery

Status: **re-audited planning contract** against `main` commit `95dd999b4678d02c10b81df059886ac3c4594ed4` (2026-10-27), including merged PRs #751, #752 and #754. The findings and delivery gates here describe inspected source, not verified browser behavior or implemented future capabilities. **Planning/documentation only; no production-code change in this audit.** Follow `AGENTS.md` and `docs/filesystem_state_contract.md`.

## North star

One creator turns an idea, gag, visual, episode, or developing narrative into **renderable short video Scenes** using one Studio Director conversation. Director is a creative collaborator **and** an operator of documented WebCap capabilities; it is not a generic chat pretending to be a video editor.

Creative discovery is flexible; production operations are precise. The initial user input may be *nothing*: opening a new Director conversation starts a one-question-at-a-time Writer's Workshop. Director can riff from a short, editable opening script, challenge weak ideas, and help discover **the core appeal**. A clear idea can become one tentative Scene immediately; a complex project can evolve one Scene at a time. There are no required title, ending, Scene count, beat map, or placeholder Scene 1/2 before a Scene 3.

### Non-negotiable interaction rules

1. **General Chat remains app-wide and unconstrained. Studio Director lives inside Studio** (the UI name for the existing Storyboard workspace). Histories remain independent; the existing app-data chat-session store is reused.
2. **Context is explicit**: navigation never attaches a Story, revises chat history, or selects an editing target. Buttons prepare **editable** instructions and **inspectable** snapshot attachments; nothing runs because of a button that merely opens Director.
3. A conversation is not *owned by* a Story or permanently bound to it. Story references in history are informational. For any real mutation, resolve an explicit stable ID and obtain fresh authoritative state. Never use a stale attachment as write authority.
4. Every mutation produces a visible before/after diff; narrow, clear changes may be applied with Undo, high-impact/structural changes require review and Apply; Director asks before extending requested scope. No silent mutations.
5. **No field explosion**: Concept (including *Core Appeal*), Style and Invariants are Director's preferred creative Story view, mapped to existing fields. Existing Guidelines and Scene subfields remain accessible; do not force migration or silently contradict established content.
6. Director knows **hard generation contracts** and existing user-editable model guidance in Settings, including *soft* empirical strengths and weaknesses. Hard generation limits are code-validated; specific limits on newly proposed Scenes are schema/parser/Apply validated. Soft guidance is advisory; do not silently change legacy scene-generation behavior.
7. A beat is not necessarily a Scene. A Scene is a renderable clip; a project can be shorter than one narrative arc or a long series. No implicit need for an intro, outro, or common formula.
8. Technical generation prompt is **derived production material**, not an additional required creative input. Director first understands the action and why it matters. Actual generated Takes and user-authored prompts are retained unless a reviewed operation changes them.
9. Loading the selected model and kicking off the first question happens **on explicit opening of a new Studio Director conversation**, not on hidden workspace startup and not on reopening an existing session.
10. Truthful progress: clear *Exploring → Draft available → Reviewed → Ready to generate → Takes*, each derived from real state. No invented percent complete, fake rewards, or score badges. Offer next actions generously sized; keep the editor visible.

## Current code: preserve and reuse

- `tool/server/storyboard_store.py`: authoritative Story JSON, stable `sceneOrder` + `scenes[id]`, tentative `add_scene`, `update_scene`, `reorder_scenes`, `update_story`, takes and prompt restore paths. `STORYBOARD_VERSION=1`. Do not rename the disk keys in this phase.
- `tool/server/app.py`: `/fs/storyboard` operations and `/fs/director/chat` / job lifecycle. `storyboard_workshop_shots` and `storyboard_story_guidelines` already support schema-constrained proposals + explicit reviews, but are separate UX paths.
- `tool/server/storyboard_llm_contract.py`, `docs/mmh3-prompt-runtime-context.txt`, `docs/storyboard-director-context.txt`: existing production constraints and prompt templates. Reuse rather than duplicate instructions, audit wording for conflicts.
- `tool/js/director_chat.js`: durable per-mode conversations recently implemented in `tool/server/director_chat_history.py`, visible/inspectable attachments, activity and model load status. Refactor **incrementally**.
- `tool/js/storyboard.js`: owner of live Studio DOM, Story/Scene editor state and save flushing. Do not let Director reach into arbitrary editor fields to create its own competing state.

### Risk to address first

Current Story attachment serializes Overview, Guidelines and only Scene titles/summaries; a specific Scene attachment contains prompt. A 'whole project' context action must **truthfully show exactly what is included**. The working Workshop snapshot currently also injects context implicitly. No new silent context. Current chat request puts attached references in the latest user message on *every turn*; this is convenient but not equivalent to immutable historical attachment messages. Make attachment a historical event in a later safe phase with explicit migrations and tests.


### Verification delta on current `main`

These are implementation-level boundaries verified after the earlier plan was written:

- **Model scope:** `tool/server/studio_director.py:guidance()` rejects every generation target other than `minimax_h3`. Settings has editable `generation_model_guidance` for **H3 and Krea2 Raw**, but only H3 is consumed by Studio today. The selected *conversation LLM* is not the same thing as the *video generation model*. New Playbook UI must not imply that Studio already supports Krea2 production planning; extend model capability dispatch only after it exists.
- **Creative data:** `_normalize_story` accepts an empty title, keeps `concept`, `style`, `invariants`, `guidelines`, and defaults `targetSceneCount` unless **explicitly passed `null`**. `_normalize_scene` keeps prompt, entry/exit states, notes, generation settings, references and Take history; its duration parsing checks a positive number but **does not itself enforce the documented 15-second production ceiling**. The actual generator validates 4–15 seconds in `storyboard_generation.py:_scene_settings`; this is a **generation-time** constraint, not a general Story edit validation. Director should know the effective limit and identify the stage that enforces it.
- **Create is not compound:** `create_story()` writes an empty Story JSON, then creates `takes/`; `add_scene()` writes a second Story version and creates a Scene Take directory after that write. Calling both in sequence does **not** satisfy reviewed atomic creation with a first Scene. Implement one *localized* compound creator, not a generic transaction engine.
- **Identity and consistency:** `story.scenes[sceneId]` and `sceneOrder` supply durable Scene identities. `invariants[]` have no IDs; Scene `invariantRefs` identify `{kind,title}`, case-insensitively. `sharedContextRefs` instead resolve IDs within legacy `development.plan.sharedContext`. Leave both reference systems intact; treat invariant rename, duplicate names, missing references and Story guideline divergence as concrete review concerns rather than inventing migration IDs.
- **Conversation fidelity:** `director_chat_history.py` saves `messages[]` as only `{role,content}`, plus a mutable `attachments{}` map, an optional `workshop` snapshot and revisioned drafts. `director_chat.js` can carry the Workshop snapshot silently in the system prompt, replaces Story attachment entries by key, and repeats attached text inside the newest user turn on every request. `prepareStudioSceneDraft()` separately sends `discussion.slice(-60)`, an unannounced context cut. A future historical event model must change this contract **compatibly**, not assume the backend already stores immutable events.
- **Editor coordination:** `window.flushStudioDirectorStoryEdits(storyId)` only flushes when that Story is already open; `flushPendingSaves()` gathers debounced Story/Scene saves and surfaces failures. `window.refreshStudioDirectorStoryIfOpen` refreshes only the active matching Story. Reuse those functions and ensure Apply does not race a later debounced save. `update_story` / `update_scene` currently have no general expected-original check; the existing reviewed Guidelines/Workshop paths do.
- **UX/verification status:** Studio already has a readable 1020px overlay, a fixed ~49vw pinned split, a 132px composer and responsive overlay fallback (`workspace_shell.css`). There is no resizable dock or expanded distraction-free layout. PR #751 explicitly left browser smoke unverified; the plan's `[x]` items mean **source + reported CI**, not a completed visual/manual acceptance gate.

## Logical data contract (existing v1 storage, no migration)

**Authoritative storage stays v1** in output/storyboards/<story-id>/story.json. The term Project is UI language, not a second object. The following mapping supersedes the previously illustrative v2 object:

| Meaning to Director | Actual canonical field | Compatibility rule |
| --- | --- | --- |
| Concept, with Core Appeal | story.concept | Core Appeal is a clear subsection or sentence **within** Concept. No persisted coreAppeal or creative object. |
| Creative vibe / visual identity | story.style | Use existing Style string and visual controls. |
| Established facts | story.invariants[] | Existing entries are {kind,title,text}; **no stable invariant ID** exists (storyboard_store.py:200-219). Avoid automatic UUID migration. |
| Renderable Scene and order | story.scenes[scene-id], story.sceneOrder[] | Scene IDs are stable; numbering is presentation only. |
| Tentative Scene intent / title | scene.summary, scene.title | No new intent field; title may be blank; prompt may be blank. |
| Model-ready prompt | scene.prompt | Existing prompt is authoritative, editable and never implicitly regenerated. |
| Physical/production state | existing durationSeconds, aspectRatio, samplingMode, references, takes, takeOrder, etc. | Preserve generation settings, references, old Takes and provenance. |
| Legacy authored planning | story.guidelines; scene.entryState / exitState / notes / invariantRefs / sharedContextRefs | Continue displaying and honoring existing populated values until reviewed consolidation. Default new extraction does not need to populate them. |

**Identity caveat:** Scene invariantRefs resolve by **{kind,title}**, not invariant UUID (storyboard_store.py:231-251,392-414). Renaming a referenced invariant must explicitly coordinate its references in reviewed Apply or surface a conflict; don't silently break them. Story/Scene reference-frame metadata is separate.

**Scene count:** `targetSceneCount` accepts null for Auto (`storyboard_store.py:_normalize_target_scene_count`); `_normalize_story` otherwise falls back to the default. The legacy New Story UI explicitly starts at 12 (`storyboard.js:createStory`); **Studio Director must send null explicitly** and must not use Scene count as evidence of an assumed Story arc.

**Unbound project.create extraction schema (proposed):**

    {
      "schemaVersion": 1,
      "operation": "project.create",
      "proposal": {
        "title": "",
        "concept": "Premise. Core Appeal: the audience anticipates the accident.",
        "style": "",
        "invariants": [{"kind": "character", "title": "Coach", "text": "Blue windbreaker"}],
        "firstScene": {"title": "", "summary": "The coach demonstrates the move."}
      }
    }

All proposal values are editable. `firstScene`, `style` and `invariants` are optional; blank title and zero Scenes are valid. Require at least an approved Concept or first-Scene idea for a meaningful creation action; do not demand a script or outline. Supply **explicit `targetSceneCount: null`** to avoid the store's default, and leave generation defaults to the existing Story normalization unless the author deliberately chooses them. Add `project.create` to the **real action affordances** and a dedicated extraction schema/route; the current informational `ACTIONS` array alone cannot execute it.

**Atomic create implementation recipe:** after parsing and editing the reviewed proposal, under the existing serialized Story mutation lock, normalize the Story and optional Scene **before** making them visible; assign IDs on the server, construct `scenes` and `sceneOrder` in memory, and commit **one JSON state**. Stage the new Story directory and empty `takes/` (and optional Scene Take directory) on the **same output filesystem**, then publish the completed directory once; clean up staging on pre-publish error, reject destination collision, and expose any publish error without claiming success. No call sequence of `create_story` then `add_scene`; no new global transaction framework. Return authoritative Story/Scene IDs, an action receipt and optional **Open Project**—never auto-attach, navigate, or rewrite the conversation. Before selecting the exact filesystem primitive, test its atomic visibility/failure behavior on supported host filesystems. A post-publish response failure must be recoverable by inspecting the created Story, not by blindly retrying creation.

### Studio Director is an H3/WebCap production expert by default — focused knowledge contract

**Expected experience:** the author can start with “I have an idea” and Director already understands that the job is to produce workable **MiniMax H3 audiovisual video in WebCap Studio**. The author supplies artistic intent and approvals, not onboarding instructions about Stories, Scenes, generation prompts, reference roles or Takes. Director is a collaborator and production advisor, not a tutorial bot: it uses relevant expertise naturally and asks one good question at a time.

**Small implicit baseline (source-owned, shipped by WebCap; no manual Settings setup required):**

1. **How Studio works:** Concept/Core Appeal + Style + Invariants form the creative brief; Scenes are independently generatable clips that can form a one-shot gag, disconnected variations or a narrative; each Scene has intent, a separately authored generation prompt, generation settings, and zero or more Takes. The normal loop is discuss → optionally capture/review Story or tentative Scene → draft/review an H3-ready prompt → generate a Take → inspect/revise/select. Creation, Apply, generation and Undo require actual WebCap actions and the author's deliberate approval. No guessed Scene count, mandatory outline or forced planning stage.
2. **H3's *actual WebCap* envelope:** `storyboard_generation.py:_scene_settings` validates **4–15 seconds** at generation time; `storyboard_store.py:_normalize_scene` itself only validates positive duration. Current generator supports text-only T2VA, first-frame I2VA, last-frame L2VA and first+last FL2VA, with exact reference alignment applied by `h3_prompt_contract.py`. Stored `guide_frame` references are *not* generatable in this path; Ref2VA is not wired. Generation controls, seed, sampling, LoRAs, aspect/size, queue, Take files and provenance belong to WebCap, not the LLM. Current Studio target model is H3 only, regardless of which local **language** model answers.
3. **Working production judgment:** choose the simplest feasible clip that conveys the Core Appeal; reason about what physically changes during the clip, action order, actor/object continuity, shot timing, motion, audio and dialogue. Suggest a reference image/first–last-frame approach when identity or a specific endpoint matters, but never pretend it guarantees consistency. Recommend breaking an idea into multiple Scenes when timing or staging warrants it, not merely because an idea has several beats. Treat model weaknesses, prompt advice and quality expectations as **empirical hypotheses** until supported by real Take evidence. Preserve authored prompts/Takes and request approval before broadening an edit.
4. **Honest WebCap affordances:** distinguish “I can discuss/propose a draft,” “WebCap has a manual UI operation,” “reviewed action is wired,” and “planned, not available.” The current `ACTIONS` array is an *informational catalog*, **not** model tool access, and is not currently sent to the model; the implementation should compose a short, accurate status-aware summary from real available affordances. Do not inject all route docs, make Director narrate its action catalog, or promise that it viewed a Take unless the needed evidence was actually supplied.

**One owner for each kind of expertise:** keep the *implicit Studio/H3 operating mental model* as a short stable server-owned baseline in `studio_director.py` or one adjacent owned guidance fragment. Read hard/conditional generation facts from tested backend operations; do not copy numerical constraints into several long prompts. Keep `docs/mmh3-prompt-runtime-context.txt` for **prompt-writing tasks**, `docs/mmh3-prompt-guidelines.md` for deeper reference, and existing `generation_model_guidance[minimax_h3]` for the user's **editable, optional** observations and proven techniques. Do not require the author to seed those Settings notes to get a competent Director. Avoid a second Playbook store or retrieval service.

**Prompt-format compatibility warning:** the current official MiniMax base guide uses cut-time notation for later shots (for example `[Shot 2] At 00:03.500`), while WebCap's runtime prompt example uses per-shot time ranges (`[Shot 1] (0s–Xs)`). These are not identical conventions. Before declaring one universally correct or rewriting existing saved prompts, compare the actual production contracts and representative generation results; use one tested prompt-authoring convention for new Studio H3 prompts, retain user-authored prompts and preserve the currently functioning Workshop parser. Source: official MiniMax `VIDEO_PROMPT_WRITING_GUIDE_base_en.md`, `docs/mmh3-prompt-runtime-context.txt`, `tool/server/storyboard_workshop.py`.

**Efficiency test:** a new unbound conversation should reveal usable production expertise **without** a long H3 lecture, copying the full example prompt, reciting UI menus or asking the author to explain WebCap. Include a small always-on core; include full H3 syntax and operation-specific details only when the task demands them. Prefer tested request assembly over an arbitrary fixed token quota.

### Conversation metadata

Retain current app-data state/director_chats/<timestamp-id>/conversation.json and its existing fields (director_chat_history.py:24-35,136-177). Preserve **original** transcript indefinitely until the user explicitly deletes it; compaction must not rewrite earlier turns. Future attachments are immutable, inspectable **historical events**, each recording the supplied snapshot, source label/ID and time; reattaching makes a new event, not a live link. No copy of the whole transcript in story.json. Store action receipts as small target/field/outcome/time summaries and optional bounded inverse patches, not duplicated prompt/response logs.

**Context budgeting:** ordinary replies stay freeform. First remove `discussion.slice(-60)` and other unannounced selection/truncation from the structured Scene extraction path, replacing it with an explicitly inspectable chosen transcript span and/or reviewed continuation summary. For each actual request, assemble workshop voice, relevant explicitly chosen historical context, recent turns and (after review) an editable concise creative-decision summary. Determine advertised/configured model context size when possible, reserve room for output and overhead, show token **estimates** as estimates. If too large, explain and offer **Compact / Select less** before sending; no hidden history truncation or automatic summary replacement. Preserve Core Appeal and committed creative decisions in the reviewed compaction. Conversation remains readable if its referenced Story is deleted. Session count/bytes and explicit clear by category belong in Settings and Storage Manager; defer auto-retention until demonstrated need.

## Text-based Director API: proposal operations, not universal chat JSON

**Ordinary brainstorming remains freeform conversation.** New Writer's Workshop exchanges must not require a tool-call schema or classify intent on every turn. A clear **user instruction** or an explicit large action button starts a separate structured **extraction/proposal** request. WebCap displays an editable proposal before a reviewed Apply. One model response never has permission to run arbitrary HTTP, write files, execute code, or replace a whole Story. The existing ACTIONS array in studio_director.py is informational, not a working tool dispatcher.

**Small, bounded versioned extraction shapes:** include schemaVersion=1, operation enum, explicit optional target IDs, changed-field object, concise rationale. Example for existing Scene revision:

    {
      "schemaVersion": 1,
      "operation": "scene.revise",
      "target": {"storyId": "story-id", "sceneId": "scene-id"},
      "changes": {"summary": "A simpler single physical action."},
      "rationale": "Preserves the gag without multiple simultaneous beats."
    }

For unbound project.create, see the reviewed creation schema above. Actual stored IDs and before-values are read by WebCap; **model-supplied IDs are never mutation authority**. Each operation gets an exact allowlist, required/optional types, bounded cardinality and strict parse. If the selected small local LLM cannot produce valid structure, preserve the chat and show the raw error/manual-edit option; never claim an action succeeded. A real-model probe is required before new structured features, not a general LLM benchmark.

**New reviewed Apply contract:** (1) explicit Story/Scene IDs or new unbound creation, never infer target from navigation; (2) flush any pending editor saves **only for the actual open target Story**, then fetch current authoritative data; (3) compare expected original values on the **affected** fields and relevant Scene order, not an unrelated whole-Story timestamp; (4) under the existing storyboard_store serialized mutation lock, merge only approved fields into a copy and write Story JSON **once**, or fail with no partial update; (5) preserve all other Scenes, prompt text, references, Takes and generation configuration; (6) report exact fields/IDs in a small conversation receipt. Overlapping edits must produce a visible conflict and a fresh review; unrelated edits should not be rejected. For multi-Scene edits, never commit one Scene and then silently fail on the next.

**Undo contract:** one reviewed coordinated action is one inverse change set. Revert only if fields still match that action's resulting values. Undo of new Scene insertion must stop if the Scene has subsequently been edited or has Takes. No unbounded Story snapshots and no generic rollback framework for unrelated historical operations. Keep revision history small and explicitly clearable, with counts. **Filesystem ownership:** reversibility metadata for durable Story/Scene author edits belongs with the owning Story (beside or within its canonical Story metadata), never as a second authoritative Story copy in app-data. Only lightweight conversational action receipts belong in app-data Director history. Use a bounded count/clear path; history deletion does not delete current Story state or Takes (docs/filesystem_state_contract.md §§1,5,10). **Story/Scene reference snapshots and continuation summaries are conversation-owned app-data state, not an alternate canonical Story store.**

**Existing button contract:** click Revise, Develop, Scene Workshop or Prepare Prompt => open Studio Director and prefill a large **editable** instruction, with precise optional context preview, **not** automatic send/Apply. Reuse existing direct editor controls when they are better than conversation; remove redundant Director-specific paths only after tested parity. Do not build a second mutation engine or a generic dispatcher until concrete duplication justifies it.

### Minimal contracts before implementing further actions

**One explicit action lifecycle:** a button only prepares an editable user instruction and a visible context selection; Send starts a bounded extraction job; the result is an uncommitted draft; Review shows target IDs, changed fields and before/after; Apply invokes a validated server operation; a successful response yields a small receipt and optional relevant editor refresh. **No automatic second model call or mutation** when opening a tool, selecting a Story, obtaining a snapshot or recognizing readiness. Keep conversational discussion separate from action proposals.

**Target and conflict contract:** a proposal carries a target `storyId` and optional `sceneId` for human review, but the server resolves both against current Story JSON on Apply. Capture expected originals from the authoritative read—not the model's narration. Check strings/scalars field by field; check `sceneOrder` as one ordered ID list for structural edits; treat `invariants[]` as a single compound field until safe element identity exists. For revisions involving referenced invariants, detect all affected `{kind,title}` links and either include explicitly approved coordinated updates or block with a clear review conflict. All changed fields/Scenes commit in one lock-held Story write. Preserve prompt/Take fields and every unrelated key. Apply response loss after a committed operation requires **read-by-target/receipt reconciliation**, never an unconditional retry.

**Undo contract detail:** inverse patch = only the selected path(s), expected post-Apply values, revision/receipt ID and timestamp. Store bounded undo metadata with the owning Story; reject undo if a touched field, order or affected Scene has changed. New Story undo must not silently erase a Story that acquired Scenes, attachments or Takes. Clearing a conversation must not clear owner-local undo or active production data.

**Compatible history/event extension:** keep the current two-role `messages[]` and revisioned `draft`, `attachments{}` and `workshop` readable. Introduce a small optional **versioned, append-only `events[]`** for newly captured context, approved action receipts and compacted-summary checkpoints: stable event ID, type, recorded timestamp, explicit source Story/Scene IDs, precise scope/field list, immutable copied content where needed, and position in the conversation timeline. Do not key event identity solely by Story ID or rewrite old messages. Show which events are included **in this request** separately from all historical events. Avoid embedding the same large snapshot in each turn: store once per deliberate capture and reference it when assembling the request. Old map-based attachments remain accessible; offer explicit conversion/reattachment only if needed. Never silently turn an old mutable pin into a dated historical event. `workshop` is legacy context, not a hidden new attachment.

**Continuation/compaction checkpoint:** the author can inspect and edit a concise summary of established facts, Core Appeal, open questions, decisions, superseded options and outstanding actions. On approval, append the checkpoint while retaining the verbatim transcript and original attachments; subsequent outbound requests use the checkpoint + explicitly selected later messages/attachment events. This is an **outbound selection**, not deletion or transcript rewriting. Estimate size of the **actually composed** request; use configured local context/calibration where available; where limit is unknown or a request exceeds it, show an actionable warning and manual selection rather than silent truncation. Implement bounded request assembly and exact request-copy inspection before claiming context safety.

**Instruction ownership and token budget:** (1) `studio_director.py` owns a brief Workshop persona; (2) server-side validated model/runtime constraints plus a **single** editable Settings Playbook own generation facts and empirical advice; (3) each extraction/action route owns its schema, output budget and field allowlist; (4) explicitly attached Story/Scene/event content owns creative facts; (5) the conversation owns dialogue and reviewed checkpoints. Retire the extra `STORYBOARD_WORKSHOP_PRIMER` from Studio only **after** tests establish equivalent voice and context; keep it for legacy flows if needed. Stop injecting `mmh3-prompt-runtime-context.txt` wholesale into freeform idea discussions; use the production prompt shape only for Scene prompt operations. Continue testing `storyboard_llm_contract.py` as a separate legacy path until parity is observed. Hard vs empirical claims must be labelled; don't turn a documented assumption into hard validation.

**Action catalog:** list operations together with status (`available` / `planned`), target types, review requirements, affected-field allowlists, accepted payload schema and error/undo behavior. Keep the **catalog inspectable** by author and model, without telling the LLM it has already called an operation. Start with concrete `project.create`, `project.brief.propose`, `scene.draft` and `scene.revise`; add move/prompt only through the same proven review pattern. Avoid a generic agent dispatcher until repeated implemented behavior requires it.

## Extracting fields from conversation

1. **Brainstorm:** natural dialogue with an implicit Writer's Workshop start; ask one useful question, allow divergence, avoid writing Story fields.
2. **Recognize readiness:** Director can say “The core appeal seems clear; draft a Scene?” This is a recommendation, not authority to mutate data.
3. **Explicit 'Capture idea / Prepare Project / Draft Scene / Propose Story brief' action:** extract agreed creative decisions from the conversation. **New Project creation needs no attached Story.** Existing-Story mutation requires an explicit target, a fresh authoritative read and narrowly selected fields. Return only affected Concept/Style/Invariants or a bounded number of candidate Scenes.
4. **Grounding/consistency:** show the key decision(s) extracted, compare to authoritative fields, flag conflicting legacy guidance and the Scenes likely affected. Ask before expanding requested scope.
5. **Review + commit:** show editable before/after per changed field; Apply checks expected original values at commit, not model memory. A multi-field action is one atomic change and one guarded Undo unit. History is bounded, counted and explicitly clearable.
6. **Producing:** after Scene intent is approved, propose the H3 prompt using the existing template. Mark readiness only when actual required prompt/settings are present. Test Takes, learn, revise locally.

## Studio UI / interaction design

- **Already implemented:** rename the visible Storyboard workspace to **Studio**; keep the existing disk/API keys and the current Scene editor/generation/Takes unchanged. This revamp targets Writer's Workshop and Director integrations, **not** a Studio-wide redesign.
- **Partially implemented:** Studio Director has a wide overlay and pinned side-by-side drawer, General Chat remains independent, and Studio exit closes the panel without deleting history. Add **user-adjustable** dock width / expanded writing view only where viewport testing justifies it, using the current drawer rather than another UI framework.
- Generous canvas: 16–18px body, 18–20px actions, clear 26px primary heading, large multi-line composer; wide model/activity controls, no micro-buttons. Dock for side-by-side Scene comparison, expand for writing.
- Empty Studio Director: strong “Let's make something” welcome + Writer's Workshop **starts on explicit opening**, loads model, asks its own first question. Reopen existing conversation => simply resume.
- **One continuous conversation**, with optional collapsible context/decisions and proposal/diff areas; not three chat modes or an always-visible control dashboard. Build the latter areas as concrete actions require them.
- Context controls show exact source, captured scope, fields and historical timestamp. Copy/inspect/remove from future inclusion must be deliberate. Opening Director via an existing button prepares editable text and a context preview; **nothing enters the request before user approval**. Only technical/model-specific production guidance is automatically supplied.
- Suggested next moves (“Explore the hook”, “Capture the idea”, “Draft one Scene”, “Prepare for H3”) are **truthful affordances**. They may populate an editable message or open a reviewed action. Avoid arbitrary scoring and fake achievements.
- Large proposal card includes *What would change*, risk, highlighted before/after, Approve/Apply, Edit, Discard; show conflicts as concrete.
- Show model loading, token activity, draft/proposal state, persistence errors. Preserve input focus and drafts across workbench switches.
